# 数据中心功能方案

**状态：** draft
**负责人：** product-and-platform
**创建日期：** 2026-08-27
**更新日期：** 2026-08-27
**关联：** [数据库数据字典](../architecture/2026-08-27-database-data-dictionary.md)、[行情数据表治理与 `bars` 淘汰实施方案](./2026-08-27-market-data-table-governance.md)、[实时快照与日 K 分时调度设计](../specs/2026-08-26-market-data-scheduling-design.md)

## 1. 方案结论

新增“数据中心”页面，定位为个人运维使用的数据观测与任务控制台，解决以下问题：

- 外部行情是否成功进入数据库；
- 当前数据覆盖到什么时间、是否存在缺口；
- AlphaFeed 与 AKShare 当前使用情况和最近切换情况；
- 数据是否满足策略、回测、详情页和收益分析的使用条件；
- 失败的同步任务如何重试，过期数据如何受控清理。

数据中心不是通用数据库后台。行情原始数据、复权数据、成交、订单、日报和审计事实均不提供在线逐行编辑功能；不提供任意 SQL 执行、任意表删除或任意字段修改。

页面采用 A 版“总览优先”作为正式信息架构：首屏显示系统健康摘要、数据域列表、质量问题和同步任务；点击数据域后在侧边抽屉中逐级查看数据域、标的和时间范围。所有操作都必须明确作用范围，质量检查默认只读数据库，只有补数和重试才允许触发外部行情源。

## 2. 已确认的边界

### 2.1 使用者

- 仅供当前用户本人运维使用；
- 沿用现有服务访问控制，不新增复杂的多角色权限模型；
- 所有高风险操作仍需二次确认；
- 页面文案和状态全部使用中文，数据源、表名和策略指标保留必要的中英文标识。

### 2.2 操作记录

- 不新增“数据中心操作审计表”；
- 不记录每次点击、每次查询和每次清理的操作日志；
- 同步任务状态与页面操作审计分离：可以持久化维护任务的运行状态、范围和结果，但不记录用户每次点击行为；
- 继续复用 `data_sync_status` 展示系统调度任务的最后状态、成功数、失败数和错误摘要；手工补数、重试和清理需要任务级状态，不能仅依赖按任务名覆盖的最后状态；
- 数据表自身的 `created_at`、`updated_at`、`fetched_at` 等字段继续保留，用于判断数据新鲜度，不作为页面操作审计。

### 2.3 任务状态边界

维护任务不是操作审计。任务状态至少需要支持：

- 多个任务同时存在；
- 任务重启后仍能查询到状态；
- 相同数据域、标的集合和日期范围的任务幂等或明确拒绝；
- 显示排队、运行中、成功、部分成功、失败、已取消等状态；
- 保存任务范围、来源策略、预计请求量、成功数、失败数和错误摘要。

第一版不要求保存每次任务的完整日志，但必须保存当前任务状态和最近结果，避免页面按钮与后台实际执行脱节。

### 2.4 数据安全边界

允许的操作：

- 运行质量检查；
- 触发单标的或指定区间补数；
- 重试失败同步任务；
- 触发受控的数据清理；
- 查看数据样本和来源。

禁止的操作：

- 在线修改行情价格、成交量、时间和来源；
- 直接修改复权因子；
- 直接删除观察池日 K、指数日 K、分钟线、订单、成交和日报；
- 任意删除数据库表；
- 输入任意 SQL；
- 绕过策略数据完整性检查强行启用数据。

## 3. 数据范围与数据域

数据中心按照业务数据域展示，而不是简单按数据库表平铺。

| 数据域 | 主要表 | 页面职责 | 默认操作 |
| --- | --- | --- | --- |
| 观察池日 K | `bar_price_tracks` | 展示 raw、qfq、复权因子和历史覆盖 | 查看、质量检查、补数 |
| 指数日 K | `index_price_tracks` | 展示基准指数的覆盖和来源 | 查看、质量检查、补数 |
| 分钟线 | `intraday_bars` | 展示分时和分钟 K 的当日覆盖 | 查看、清理、补数 |
| 实时快照 | `market_quotes` | 展示当前交易日的最新行情和延迟 | 查看、质量检查、清理 |
| 行情采集诊断 | `market_quote_events` | 展示最近 7 天来源、切换和异常 | 查看、按保留期清理 |
| 同步任务 | `data_sync_status` | 展示行情、指数、目录和外部数据任务状态 | 查看、重试 |
| 标的目录 | `instrument_catalog` | 展示代码、名称、类型和同步日期 | 查看、全量刷新 |
| 交易日历 | `trading_calendar` | 展示 A 股、港股、美股覆盖情况 | 查看、刷新 |
| 外部市场数据 | `overseas_market_data`、`futures_positions` | 展示外部市场数据状态，明确不进入 A 股持仓和收益 | 查看、刷新 |
| 龙虎榜与辅助数据 | `lhb_records`、`lhb_seat_profile`、`lhb_quant_seats`、`instrument_sector_mapping` | 展示策略辅助数据的覆盖和新鲜度 | 查看、补数 |

数据中心不得把外部市场数据误显示为 A 股组合行情。页面需持续标注：**外部市场数据仅参与策略分析，永远不进入持仓和收益统计。**

### 3.1 统一数据域摘要

所有数据域在首页使用统一的摘要口径，不因底层表结构不同而改变信息层级。每个数据域必须提供以下字段：

| 字段 | 说明 |
| --- | --- |
| `dataset` | 稳定的数据域标识，不直接使用可变的页面文案 |
| `name` | 中文数据域名称 |
| `tables` | 关联表名，允许多个 |
| `status` | `正常`、`部分缺失`、`同步中`、`降级`、`失败` |
| `record_count` | 当前统计范围内的有效记录数 |
| `coverage` | 按该数据域规则计算的覆盖率 |
| `symbol_count` | 已覆盖标的数与预期标的数 |
| `earliest_at` / `latest_at` | 当前范围内最早和最新数据时间 |
| `source` | 最近成功来源或来源组合 |
| `latency_seconds` | 数据延迟；不适用时返回空值 |
| `issue_count` | 当前未解决质量问题数 |
| `affected_modules` | 受影响的策略、回测、详情页或收益分析模块 |
| `available_actions` | 当前状态允许的受控操作 |

状态、操作和空状态文案全页面统一。首页只展示摘要，详情页再展示不同数据类型的专属字段。

### 3.2 数据类型专属字段

- 日 K：交易日覆盖、raw/qfq/factor 三轨完整性、缺失交易日；
- 分钟线：交易日、交易时段、分钟粒度、缺失时间段和当日点数；
- 实时快照：最新观察时间、延迟、当日快照数量和每个标的的最新价格；
- 行情诊断：AlphaFeed/AKShare 来源占比、限流、熔断、切换和错误类型；
- 外部市场：市场、标的、最近交易日和 `external_only` 标记，禁止归入 A 股组合统计。

## 4. 页面信息架构

### 4.1 顶部总览区

首屏展示当前系统数据健康度：

- 数据域总数；
- 正常、降级、失败的数据域数量；
- 最近一次成功同步时间；
- 最老未补齐的历史数据日期；
- 当前 AlphaFeed 状态；
- AKShare 备用状态；
- 待处理质量问题数量；
- 当前是否存在策略因数据缺失而失效的标的。

顶部只展示摘要，不把所有表的明细一次性加载进首屏。

### 4.2 数据域列表

每个数据域以紧凑列表项展示：

- 数据域名称；
- 关联表名；
- 当前状态：正常、部分缺失、同步中、降级、失败；
- 数据行数；
- 标的数量；
- 最早时间；
- 最新时间；
- 最近来源；
- 数据延迟；
- 质量问题数；
- 查看详情和可用操作。

数据域过多时使用分页或滚动容器，不能撑高整个页面。

### 4.3 数据详情抽屉

点击数据域后打开详情抽屉，不跳离数据中心。抽屉包含：

- 数据域级覆盖摘要：记录数、覆盖率、最早/最新时间、来源、延迟和受影响模块；
- 按标的的覆盖列表：代码、名称、状态、预期记录数、实际记录数、缺失数、最新时间和质量结论；
- 选中单个标的后的二级诊断：缺失日期、时间段断档、来源占比、最近失败和策略影响；
- 样本数据预览：只读、分页、限制返回数量，并按数据域提供统一的时间、标的、价格、来源和抓取时间字段；
- 质量检查结果：检查项、失败记录数、严重程度、影响范围和建议动作；
- 作用域明确的补数、重试或清理操作。

原始数据样本默认只读，并限制返回数量，避免一次加载整张表。

详情抽屉使用固定的信息层级：`概览`、`标的覆盖`、`缺口诊断`、`来源与失败`、`样本预览`、`操作`。不同数据域可以隐藏不适用的字段，但不能改变基础信息的顺序和含义。

### 4.4 数据质量面板

质量面板按严重程度分组：

- 阻断：会导致策略或页面不能安全使用；
- 警告：数据可用但存在覆盖或延迟问题；
- 提示：来源切换、近期清理或非交易日等信息。

每条问题必须显示数据域、标的、时间范围、问题类型、影响范围和建议动作。

### 4.5 同步任务面板

系统调度任务读取 `data_sync_status`；页面发起的补数、重试和清理任务读取任务级状态，统一展示：

- 任务 ID；
- 任务名称；
- 数据域；
- 任务范围：标的、日期、数据轨道和来源策略；
- 最近开始和结束时间；
- 当前进度；
- 成功数；
- 失败数；
- 使用来源；
- 当前状态；
- 错误摘要；
- 重试按钮。

重试按钮只允许对失败、部分成功或降级任务使用；运行中的相同范围任务不可重复提交。任务列表使用分页或内部滚动，不撑高整页。

### 4.6 数据清理面板

只展示符合既定保留策略的清理项：

- `market_quote_events`：保留 7 天；
- `market_quotes`：清理非当前交易日快照；
- `intraday_bars`：按交易日和保留策略清理；
- 过期目录或临时同步数据：仅在明确配置后清理。

清理前展示预计影响行数和时间范围，并要求二次确认。核心历史行情、订单、成交和日报不出现在清理列表中。

## 5. 数据质量规则

### 5.1 覆盖完整性

以 `trading_calendar` 为预期交易日基准：

```text
覆盖率 = 已有有效交易日数量 / 预期交易日数量
```

检查内容：

- 配置区间内是否存在缺失交易日；
- 最新数据是否达到应有日期；
- 是否存在连续断档；
- 观察池标的是否达到策略所需最小历史长度；
- 指数数据是否覆盖盈亏分析选择的区间。

缺失数据时沿用现有规则：策略数据视为失效，禁止该策略触发交易。

### 5.2 价格与字段合理性

检查：

- `open_price`、`high_price`、`low_price`、`close_price` 大于零；
- `high_price >= max(open_price, close_price)`；
- `low_price <= min(open_price, close_price)`；
- 成交量和成交额不为负；
- 时间戳按数据域单调递增且没有异常未来时间；
- raw、qfq、复权因子能够按交易日对应；
- 不复权价格用于持仓估值和实际收益，前复权价格用于技术指标和回测。

### 5.3 重复与唯一性

按目标表主键检查重复：

- `bar_price_tracks`：`symbol + interval_name + timestamp_value`；
- `index_price_tracks`：`symbol + interval_name + timestamp_value`；
- `intraday_bars`：`symbol + interval_name + timestamp_value`；
- `market_quotes`：`trade_date + symbol + observed_at`。

数据库主键冲突应通过幂等 upsert 处理，质量面板仍需报告重复输入或重复采集现象。

### 5.4 来源与新鲜度

展示并检查：

- 最近来源是 AlphaFeed 还是 AKShare；
- 是否发生过主备切换；
- 最近成功同步距当前时间；
- 交易时段实时快照是否超过允许延迟；
- 非交易时段日 K 是否在规定窗口完成；
- 失败是否达到熔断阈值。

数据中心不改变现有主备切换策略，只提供可解释的状态和手工重试入口。

## 6. 页面操作规则

### 6.1 补数

补数操作必须选择：

- 数据域；
- 标的或标的集合；
- 起止日期；
- 数据来源策略：默认主源优先、备用源兜底。

提交前展示预计范围和影响：

- 预计标的数量；
- 预计交易日数量；
- 是否需要同时请求 raw 和 qfq；
- 预计 AlphaFeed 请求量；
- 是否可能触发限流。

全量补数需要二次确认；重复提交同一范围时应被拒绝或提示已有任务运行中。

补数流程为：选择数据域 → 选择一个或多个标的 → 选择起止日期 → 选择来源策略 → 预览影响 → 二次确认 → 创建异步任务。页面不得用一个无范围的“发起补数”按钮直接触发全表同步。

质量检查与补数必须分离：质量检查只查询数据库和交易日历，不主动请求 AlphaFeed 或 AKShare；补数任务才按现有主源优先、备用源兜底和限流策略调用外部接口。

### 6.2 重试

重试只针对失败任务或失败标的，不默认扩大日期范围。重试前显示最近失败原因，包括：

- 网络错误；
- 主源限流；
- 主源返回空数据；
- 解析失败；
- 数据库写入失败。

### 6.3 清理

清理操作只能选择系统提供的保留策略，不能输入任意日期和表名。页面显示：

- 清理对象；
- 保留规则；
- 预计删除数量；
- 是否会影响详情页或策略。

### 6.4 质量检查

质量检查默认只读、可重复执行，不改变行情数据。检查结果直接返回当前状态，不新增操作审计记录。

质量检查按数据域、标的和日期范围执行，默认优先使用索引、聚合字段和有界查询，不扫描整张历史事实表。短时间内重复点击同一检查范围时应复用正在运行的检查或返回最近结果，不产生外部行情请求。

## 7. 后端接口草案

接口命名以数据中心为边界，避免把多个数据域重新拼成一个超大接口。

```text
GET  /api/data-center/overview
GET  /api/data-center/datasets
GET  /api/data-center/datasets/{dataset}/summary
GET  /api/data-center/datasets/{dataset}/coverage
GET  /api/data-center/datasets/{dataset}/samples
GET  /api/data-center/quality
GET  /api/data-center/tasks
POST /api/data-center/quality/check
POST /api/data-center/tasks/{task}/retry
POST /api/data-center/backfill
POST /api/data-center/cleanup
```

接口要求：

- 每个接口只返回当前页面需要的数据；
- 列表、覆盖明细和样本数据分页或限制数量；
- 详情接口支持 `symbol`、`start_date`、`end_date` 和分页参数；
- 任务提交返回 `task_id` 和任务状态，不同步等待整段补数完成；
- 正在运行的同类任务需要按数据域、标的集合、日期范围和数据轨道幂等或明确拒绝；
- 质量检查接口不得触发外部行情请求；
- 补数预览接口需要返回预计标的数、交易日数、请求次数和限流风险；
- 不提供 SQL 参数；
- 不返回数据库密码、连接串、API Key 或内部凭据；
- 外部市场数据接口必须带 `external_only` 或等价语义，避免前端误归入 A 股收益。

## 8. 持久化与数据库方案

第一版不新增数据质量快照表，复用现有数据表和 `data_sync_status`。但为支持页面发起的异步维护任务，允许新增任务运行状态表，或将现有同步状态扩展为任务级模型：

- 数据量、时间范围和来源从目标行情表聚合；
- 质量检查结果实时计算；
- 同步状态读取 `data_sync_status`；
- 清理动作复用现有存储层方法；
- 系统定时任务继续使用 `data_sync_status`；
- 手工补数、重试和清理任务必须保存任务 ID、范围、状态、进度和结果；
- 任务状态不是页面操作审计，不保存每次点击和完整操作日志。

暂不持久化每次质量检查结果，也不持久化每次页面操作记录。后续如果需要绘制质量趋势，再单独评估 `data_quality_snapshots`，不能把质量快照混入行情事实表。

若复用 `data_sync_status`，至少需要将唯一键从单一 `task_name` 扩展为可区分任务实例和作用范围的模型；不允许通过覆盖同一行来伪装任务队列。

## 9. 分阶段实施计划

### 阶段一：后端聚合与接口

1. 增加数据域注册表和统一的数据域描述；
2. 定义统一数据域摘要契约和不同数据类型的专属字段；
3. 实现总览、数据域摘要、单标的覆盖、缺口和样本查询；
4. 接入 `data_sync_status`，并建立任务级状态模型；
5. 增加只读数据质量规则服务；
6. 为补数、重试、质量检查和清理建立受控命令接口；
7. 在服务端限制范围、并发、幂等和危险操作；
8. 确认质量检查不会调用外部行情接口，补数才允许触发主备数据源。

### 阶段二：React 页面

1. 新增“数据中心”Tab；

### 阶段三：联调与验收

1. 使用 Mock 数据覆盖正常、空数据、部分缺失、主备切换和失败场景；
2. 验证数据中心操作不会绕过策略数据失效规则；
3. 验证首页和详情页使用统一摘要字段与状态语义；
4. 验证按单标的查看覆盖、缺口、来源和样本；
5. 验证补数任务不会重复提交、扩大范围或绕过限流预览；
6. 验证质量检查不会触发外部行情请求；
7. 验证外部市场数据不会进入持仓和收益接口；
8. 验证首屏不加载整张大表，详情和样本均分页或限量；
9. 验证服务重启后仍可查询已创建维护任务的状态；
10. 验证移动端和桌面端列表、抽屉和确认弹窗可用。

## 10. 验收标准

- 能在一个页面看到所有外部数据域的当前状态；
- 所有数据域使用统一摘要字段和状态语义；
- 能按数据域进一步查看单个标的的行数、覆盖范围、缺口、来源和新鲜度；
- 能定位缺失交易日、断档、异常价格、重复输入和来源切换；
- 能看到维护任务的范围、状态、进度、成功数、失败数和错误摘要；
- 能对失败任务执行受控重试，且服务重启后任务状态不丢失；
- 能对指定范围发起补数，并在提交前看到范围和限流风险；
- 质量检查只读数据库，不因页面检查动作触发外部行情请求；
- 能按既定保留策略清理允许清理的数据；
- 不允许页面修改核心行情事实或执行任意 SQL；
- 不新增操作审计表，不影响现有交易审计和数据同步状态；
- 数据中心接口不会返回全量大表，首屏加载不依赖所有明细接口；
- 观察池、指数、分钟线和实时快照继续使用各自的专用数据表；
- 数据中心显示的外部市场数据不会进入 A 股持仓和收益统计。

## 11. 暂待评审的问题

本方案进入实现前，需要重点评审以下问题：

1. 维护任务状态是新增任务表，还是扩展现有 `data_sync_status` 为任务实例模型；
2. 第一版是否需要保存任务历史，还是只保留运行中和最近结果；
3. 分钟线的保留期是否沿用当前策略，还是在数据中心中增加可配置项；
4. 数据域详情的样本字段是否按统一字段加数据域专属字段实现；
5. 是否需要为数据中心单独增加访问入口开关。

在任务状态模型、补数范围和质量检查不触发外部接口这三个边界确认前，不开始修改数据库结构和正式页面。当前原型仅用于评审信息架构，不视为功能已实现。
